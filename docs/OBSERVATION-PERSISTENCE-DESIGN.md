# Observation Provenance and Persistence Design

Status: schema and database persistence primitives committed; execution-boundary and immutable-blob integration remain incomplete.
Date: 2026-11-20.

## Decision

Keep ARTEX's existing records authoritative:

- `assets` remains the current entity inventory and latest-known projection.
- `findings` remains the vulnerability/finding record and its verification/report lifecycle.
- `exploration_nodes` facts remain task-scoped reasoning, including positive, negative and third-party intelligence.
- The existing evidence package remains the owner of immutable evidence bytes and content hashes.

Add a narrow append-only provenance layer that records *which source claim produced or updated which existing record*. It must not become a second asset, finding, or graph store.

## Current implementation facts and gaps

1. `normalizer.Observation` already defines typed claims, identity keys, source tool/version, source run, task, timestamp, evidence refs, scope, confidence, verification and collection status.
2. Scanner adapters currently emit normalized projections in tool responses. They do not durably store these projections as claims.
3. The adapters currently use a generated ingestion-attempt string as `source_run_id`, not a scanner execution ID. This must not be presented as a process/run identifier.
4. The adapter's `artifact://<basename>` value is only a locator hint. It is not a registered immutable evidence object, and basename collisions are possible.
5. `evidence.Store` already stores HTTP traffic request/response bodies as SHA-256-addressed files and verifies byte length and digest. Its current API and DB metadata are traffic/finding-oriented; it does not expose a generic scanner-artifact registration contract.
6. `agent.RunInfo` carries task, exploration, intent and session attribution, but no stable external process execution ID.
7. Existing asset upserts merge the current projection and refresh last_seen. Exploration facts and findings retain their own domain-specific detail. None alone is a complete append-only normalized observation history.

### A. Collection execution

The schema and DB API now provide `collection_runs` records. They must be created by the caller for each actual tool process or external collection execution, with:

- `id`: UUID generated by ARTEX before process launch; this is the canonical `source_run_id`.
- `task_id`, optional `exploration_id`, optional `intent_id`.
- `source_tool_id`, optional observed `source_tool_version`.
- `execution_mode` and platform as observed metadata, not inferred permissions.
- `started_at`, optional `finished_at`, `status` (planned/running/succeeded/partial/failed/cancelled).
- Safe execution metadata only: working-directory-relative output locator, exit code, and bounded non-secret metadata. Never persist credentials, tokens, environment secrets or unredacted command arguments by default.

Create the run at the execution boundary, not during ingestion. Pass its ID through the tool execution context to the output writer and ingestion adapter. If an existing execution path cannot supply it, the adapter must mark run provenance unavailable and emit a warning; it must not invent a run ID.

A scanner invocation that produces multiple files shares one run ID. A retry/new process gets a new run ID. Re-ingesting the same artifact for the same run is an idempotent replay.

### B. Immutable generic artifacts

Pending: extend the existing evidence package with a generic artifact API rather than writing an independent evidence store:

- Register a regular file/stream into the existing content-addressed blob layout.
- Compute SHA-256 and byte length while copying; never trust a caller-supplied digest.
- Return an opaque stable evidence ID plus digest, length, media type, and creation time.
- Store metadata linking artifact to collection run, task, source tool, original relative path and capture time.
- Keep raw bytes immutable. Redaction/derived representations are separate artifacts linked to the original; never rewrite the original.
- Apply bounded size, file-type, path confinement, permissions and retention/GC rules. Do not follow symlinks outside the run directory.
- Use opaque IDs in API payloads; do not expose filesystem paths.

Traffic request/response evidence remains compatible and may share the blob primitives. It must not be silently reinterpreted as a scanner artifact.

### C. Append-only observation claims

The `observation_claims` relation is now present, keyed by `observation_id` (primary key), with:

- `identity_key` (indexed, deliberately not unique), observation type and normalized target/locator fields.
- `source_tool_id`, optional tool version, `source_run_id`, `task_id`, `observed_at`.
- `evidence_id` and SHA-256 digest; require at least one registered evidence object for durable scanner claims.
- scope, confidence, verification and collection status as explicit enums/check-constrained text.
- claim value and bounded attributes JSONB.
- nullable links to existing `asset_id`, `finding_id`, and `exploration_node_id`; each FK uses `ON DELETE SET NULL` so claim history survives deletion of a projection.
- `created_at` for ingestion time, distinct from `observed_at`.

Use a separate join relation if a single claim needs multiple evidence objects. Do not duplicate evidence bytes in JSONB. Do not make `identity_key` unique: distinct runs and contradictory source claims must coexist.

### D. Idempotency and conflicts

- `observation_id` is the exact-claim replay key. A duplicate insert is a no-op only when the stored canonical payload matches; if the same ID arrives with different payload, return a conflict/error and preserve the original.
- `identity_key` groups claims about the same entity but never overwrites history.
- Different run IDs, sources, timestamps, values or state labels remain separate claims.
- Current `assets` projection continues to use existing upsert logic. Claim persistence and projection links should be committed in one DB transaction where possible.
- A failure to persist the claim must be visible as an ingestion error; do not report the observation as durably recorded just because the asset upsert succeeded.
- Retain existing task-scope gates. Out-of-scope claims can be retained as intelligence but cannot create task-scope entries.

## Transaction and lifecycle

1. Create `collection_runs` at process launch and transition its status on exit.
2. Register the raw output as an immutable evidence artifact before parsing. A truncated/partial artifact remains retained and the run status reflects partial collection.
3. Parse output and build normalized observations using the real run ID and registered evidence ID/digest.
4. Validate each observation; reject missing task/run/evidence provenance for durable scanner claim writes.
5. Upsert/link the existing asset or record the appropriate exploration fact/finding under existing policy.
6. Insert append-only observation claim(s) and link them to the existing record(s), transactionally where the current store boundaries allow.
7. Return counts for parsed, projected, claim-persisted, replayed, rejected and failed items. Never conflate asset writes with claim persistence.
8. Keep failed/partial run records and evidence for operator diagnosis under configured retention; do not manufacture tested-negative claims from missing output.

## Migration sequence (future work; not applied)

1. Wire the existing `collection_runs` and generic artifact metadata APIs into the actual process launch/exit boundary after confirming the runner lifecycle and output capture path.
2. Add `observation_claims` and evidence join table with FK/index/check constraints.
3. Add DB methods and transaction-aware APIs; test duplicate replay, conflicting claims, FK deletion behavior and transaction rollback.
4. Wire actual execution IDs at the process launch boundary; update scanner adapters to accept registered evidence references.
5. Integrate asset/fact/finding projection links without changing existing API response semantics.
6. Add authenticated read APIs and operator provenance UI only after access-control review.
7. Backfill no historical run IDs or evidence digests by guessing. Legacy rows remain explicitly legacy/unknown provenance.

### Implemented lineage guard (2026-11-20)

`InsertObservationClaim` now inserts only when the registered evidence artifact and its parent collection run both match the claim's `source_run_id`, `task_id` and `source_tool_id`. This prevents a valid artifact/run pair from being reused to attribute a claim to another task or tool. PostgreSQL regression cases cover mismatched task and tool identities; execution remains pending.

## Acceptance tests required before calling this job implemented

- Run ID is generated at execution launch and remains identical from process through ingestion; retries receive different IDs. (UUID helper and DB creation API exist; launch-boundary wiring remains pending.)
- Artifact registration computes and verifies digest/length, is immutable, and safely handles duplicate content. (Not yet implemented; metadata table/API only.)
- Path traversal, symlink escape, non-regular files and over-limit artifacts fail closed.
- Observation claim insert is idempotent for identical replay and rejects same-ID/different-payload collision. (DB method and PostgreSQL test added; test not run.)
- Same identity with contradictory claims retains both rows.
- Asset/finding/node deletion nulls only the projection link and preserves the claim.
- Transaction failure leaves no falsely reported durable claim.
- Out-of-scope observations cannot enter task scope.
- Partial/failed runs and their evidence remain distinguishable from tested-negative results.

## Explicit non-goals

- No second asset inventory or replacement exploration graph.
- No automatic vulnerability confirmation from scanner matches.
- No fabricated execution IDs, evidence IDs, digests, versions or confidence.
- No execution permission implied by catalogue presence, agent compatibility or provenance.
- No migration or backfill until the existing task schema and artifact lifecycle are reviewed against this design.
